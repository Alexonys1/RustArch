# RustArch

Это многопоточный архиватор на Rust, написанный студентами ПИН третьего курса: Бондарем А.В. и Волгиным Н.А.

## Возможности

- многопоточная архивация и разархивация;
- выбор алгоритмов сжатия: Huffman, LZSS, Deflate (LZSS + Huffman);
- шифрация через XOR;
- защита данных кодом Рида-Соломона;

## Сборка и запуск

Rust edition >=2024.

```text
cargo build --release
cargo test
```

## Основные команды:

```text
rustarch pack <SOURCE> <ARCHIVE> [OPTIONS]
rustarch unpack <ARCHIVE> <DESTINATION> [OPTIONS]
rustarch list <ARCHIVE>
rustarch help
```

Алгоритм сжатия задаётся через `-c` или `--compression`: `none`, `rle`,
`huffman`, `lzss`, `deflate`. По умолчанию используется `deflate`.

```text
rustarch pack ./data backup.rarc -c lzss
rustarch pack ./data backup.rarc -c deflate --fec reed-solomon
rustarch pack ./data backup.rarc --cipher xor --key-file ./key.bin
rustarch unpack backup.rarc ./restored --key-file ./key.bin
rustarch list backup.rarc
```

## Общие соглашения

- Все целые числа в байтовых структурах хранятся в little-endian, если явно
  не указано иное.
- Смещения архива абсолютные и отсчитываются от начала файла (ноль).
- Пути кодируются UTF-8 и используют `/` как разделитель.
- Размер пути измеряется в байтах UTF-8, а не в символах.
- Битовый поток Huffman записывается старшими битами вперёд.
- Типы `usize`, указатели и внутреннее представление перечислений языка в
  архив не записываются.
- Текущая версия формата - 3. Совместимость с предыдущими вариантами формата
  не поддерживается, т.к. изначально заголовок архива хранился в начале файла,
  а не в конце, как сейчас.

## Общая структура архива

В начале архива нет отдельного заголовка или сигнатуры. Сигнатура и параметры
контейнера находятся в фиксированном footer в конце файла.

```text
0 - начало файла
├─ payload файлов
├─ таблица файлов
├─ таблица пустых директорий
└─ footer, 32 байта
EOF
```

Пусть:
- `A` - полный размер архива;
- `T` - `table_offset` из footer;
- `S` - `table_size` из footer.

Тогда области архива имеют следующие границы:

| Область         |   Начало | Конец не включительно | Размер |
|-----------------|---------:|----------------------:|-------:|
| Payload         |      `0` |                   `T` |    `T` |
| Таблицы записей |      `T` |               `T + S` |    `S` |
| Footer          | `A - 32` |                   `A` |     32 |

Обязательное соотношение:

```text
T + S = A - 32
```

Payload ненулевой длины должны образовывать непрерывную непересекающуюся
область `[0, T)`. Порядок payload определяется фактическим завершением
параллельной упаковки и не обязан совпадать с порядком исходных файлов.

## Footer архива

Footer всегда занимает последние 32 байта архива.

| Смещение от footer | Размер | Тип       | Поле              | Значение                          |
|-------------------:|-------:|-----------|-------------------|-----------------------------------|
|                `0` |      4 | `[u8; 4]` | `magic`           | ASCII `RARC`, байты `52 41 52 43` |
|                `4` |      2 | `u16`     | `version`         | `3`                               |
|                `6` |      2 | `u16`     | `flags`           | Сейчас обязательно `0`            |
|                `8` |      8 | `u64`     | `table_offset`    | Абсолютное начало таблицы файлов  |
|               `16` |      8 | `u64`     | `table_size`      | Общий размер обеих таблиц         |
|               `24` |      4 | `u32`     | `file_count`      | Количество файловых записей       |
|               `28` |      4 | `u32`     | `directory_count` | Количество записей директорий     |


## Запись файла `ArchivedArtifactEntry`

Пусть `N` - значение `path_len`.

| Смещение от записи | Размер | Тип       | Поле             | Описание                                               |
|-------------------:|-------:|-----------|------------------|--------------------------------------------------------|
|                `0` |      2 | `u16`     | `path_len`       | Длина пути в байтах UTF-8                              |
|                `2` |    `N` | `[u8; N]` | `relative_path`  | Относительный путь UTF-8                               |
|            `2 + N` |      8 | `u64`     | `original_size`  | Размер исходного файла до pipeline                     |
|           `10 + N` |      8 | `u64`     | `stored_size`    | Размер payload после всего pipeline                    |
|           `18 + N` |      8 | `u64`     | `payload_offset` | Абсолютное смещение payload относительно начала архива |
|           `26 + N` |      4 | `u32`     | `crc32`          | CRC32 исходных данных                                  |
|           `30 + N` |      2 | `u16`     | `pipeline`       | Дескриптор применённых алгоритмов                      |

Полный размер записи файла (`ArchivedArtifactEntry`):

```text
32 + N байт
```

Payload файла занимает полуинтервал:

```text
[payload_offset, payload_offset + stored_size)
```

Для payload нулевой длины несколько записей могут иметь одинаковое смещение.

### Поле `crc32`

Используется полином CRC32 IEEE 802.3. Контрольная сумма считается по исходным
данным до сжатия, шифрования и FEC.

## Запись пустой директории `ArchivedDirectoryEntry`

Записываются только директории, которые обходчик определил как пустые.

| Смещение от записи | Размер | Тип       | Поле            | Описание                  |
|-------------------:|-------:|-----------|-----------------|---------------------------|
|                `0` |      2 | `u16`     | `path_len`      | Длина пути в байтах UTF-8 |
|                `2` |    `N` | `[u8; N]` | `relative_path` | Относительный путь UTF-8  |

Полный размер записи:

```text
2 + N байт
```

## Дескриптор `PipelineSettings`

Структура Pipeline хранится в архиве как одно значение `u16`.

|      Биты |    Маска | Поле           | Допустимые значения |
|----------:|---------:|----------------|---------------------|
|   `0..=3` | `0x000F` | Compression ID | `0..=4`             |
|   `4..=7` | `0x00F0` | Cipher ID      | `0..=1`             |
|  `8..=11` | `0x0F00` | FEC ID         | `0..=1`             |
| `12..=15` | `0xF000` | Reserved       | Обязательно `0`     |

### Compression ID

| ID | Алгоритм                 |
|---:|--------------------------|
|  0 | Без сжатия               |
|  1 | RLE                      |
|  2 | Huffman                  |
|  3 | LZSS                     |
|  4 | Deflate (LZSS + Huffman) |

Компрессор может вернуть другой эффективный ID. Например, LZSS или Huffman
могут вернуть исходный `Artifact` и ID `0`, если сжатие признано невыгодным.
В файловую запись сохраняется именно эффективный ID.

### Cipher ID

| ID | Алгоритм       |
|---:|----------------|
|  0 | Без шифрования |
|  1 | XOR            |

### FEC ID

| ID | Алгоритм                 |
|---:|--------------------------|
|  0 | Без FEC                  |
|  1 | Reed–Solomon RS(255,223) |

## Порядок обработки данных (pipeline)

При упаковке этапы применяются в следующем порядке:

```text
исходные данные
-> compression
-> cipher
-> FEC encode
-> постановка в очередь за запись сжатых данных в конечный архив
```

При распаковке выполняется обратная последовательность:

```text
payload архива
-> FEC decode
-> cipher transform
-> decompression
-> сброс данных на диск
```

`stored_size` описывает внешний результат после FEC. Формат конкретного
компрессора может быть скрыт шифрованием и дополнительно обёрнут FEC.

## Без сжатия

Данные записываются как есть. Заголовка нет.

## RLE

RLE не имеет собственного заголовка. Поток просто состоит из пар до конца payload.

| Смещение от пары | Размер | Тип  | Поле    | Описание                                                    |
|-----------------:|-------:|------|---------|-------------------------------------------------------------|
|              `0` |      1 | `u8` | `count` | Число повторений, создаваемое кодером в диапазоне `1..=255` |
|              `1` |      1 | `u8` | `value` | Повторяемый байт                                            |

Размер каждой пары - 2 байта. Серия длиннее 255 байт разбивается на несколько
пар. Декодер заканчивает работу по концу payload, известному из `stored_size`
после снятия внешних FEC и cipher.

## Huffman

### Заголовок

Пусть `K` - число различных символов.

| Смещение | Размер | Тип   | Поле                  | Описание                |
|---------:|-------:|-------|-----------------------|-------------------------|
|      `0` |      2 | `u16` | `nonzero_freqs_count` | `K`, диапазон `0..=256` |
| `2 + 9i` |      1 | `u8`  | `symbol[i]`           | Значение символа        |
| `3 + 9i` |      8 | `u64` | `frequency[i]`        | Частота символа         |

Здесь `i = 0..K-1`. Размер заголовка:

```text
2 + 9K байт
```

Таблица содержит только символы с ненулевой частотой. Размер результата
Huffman равен сумме всех частот, поэтому отдельный
`original_size` в потоке не хранится.

### Битовое тело

Битовое тело начинается по смещению `2 + 9K`.

- Коды записываются `MSB-first`.
- Переход по левой ветви дерева добавляет бит `0`, по правой - `1`.
- Последний байт дополняется нулевыми битами справа.
- Длина битового тела отдельно не хранится.
- Декодирование останавливается после получения `sum(frequency)` байт.
- При `K = 0` или `K = 1` битовое тело отсутствует.

Дерево восстанавливается из частот. Символы в заголовке записываются в порядке
возрастания значения байта; при равных частотах построитель использует
детерминированный последовательный номер узла.

Текущая реализация хранит код в `u32`.

## LZSS

LZSS не имеет собственного заголовка. Поток сразу начинается с групп максимум
по восемь токенов. Декодер получает размер исходного файла из
`ArchivedArtifactEntry.original_size`.

### Группа токенов

```text
flags: u8
body(token 0)
body(token 1)
...
body(token 7)
```

Токен `i` описывается битом `i` байта `flags`, то есть биты используются от
младшего к старшему (`LSB-first` внутри байта флагов):

- `0` - одиночный литерал;
- `1` - match или последовательность литералов.

Последняя группа может содержать меньше восьми токенов. Декодер определяет её
конец по достижению `original_size`; неиспользуемые старшие биты флагов равны
нулю.

### Одиночный литерал

Используется при соответствующем бите `flags = 0`.

| Смещение от тела | Размер | Тип  | Поле      |
|-----------------:|-------:|------|-----------|
|              `0` |      1 | `u8` | `literal` |

### Match

Используется при бите `flags = 1` и `offset != 0`.

| Смещение от тела | Размер | Тип   | Поле             | Описание               |
|-----------------:|-------:|-------|------------------|------------------------|
|              `0` |      2 | `u16` | `offset`         | Расстояние назад       |
|              `2` |      1 | `u8`  | `length_minus_3` | Реальная длина минус 3 |

Реальная длина:

```text
length = length_minus_3 + 3
```

Диапазон длины - `3..=258`. Текущее окно поиска - 32 КиБ, хотя поле offset
позволяет хранить значения до 65535.

### Последовательность литералов

Используется при бите `flags = 1` и `offset = 0`.

| Смещение от тела | Размер | Тип | Поле | Описание |
|---:|---:|---|---|---|
| `0` | 2 | `u16` | `offset` | Всегда `0` |
| `2` | 2 | `u16` | `run_len` | Число следующих literal |
| `4` | `run_len` | `[u8; run_len]` | `bytes` | Несжатые байты |

Кодер использует этот тип для последовательностей длиной не меньше 34 байт.
Максимальная длина одной последовательности - 65535 байт.

Отдельного байта `compressed/stored` в текущем формате нет. Если LZSS
отказывается от сжатия, в файловой записи сохраняется Compression ID `0`, а
payload остаётся исходным.

## Deflate

Это не настоящий Deflate и поэтому не совместим с RFC 1951 и ZIP Deflate.

Кодер последовательно пробует два этапа:

```text
исходные данные -> LZSS -> Huffman
```

Каждый этап может отказаться от сжатия. В запись архива сохраняется фактически
получившийся Compression ID:

| LZSS | Huffman | Итоговый ID |
|:----:|:-------:|-------------|
|  +   |    +    | Deflate     |
|  -   |    +    | Huffman     |
|  +   |    -    | LZSS        |
|  -   |    -    | Без сжатия  |

Для ID Deflate распаковка выполняется в обратном порядке:

```text
Huffman decode -> LZSS decode
```

Huffman восстанавливает длину промежуточного LZSS-потока по сумме частот.
LZSS получает конечный размер исходного файла из `ArchivedArtifactEntry`.
Раньше каждый алгоритм отдельно хранил поле `original_size` где-то у себя
внутри файла. Потом мы это убрали за ненадобностью.

## XOR

XOR не добавляет заголовок и не меняет размер payload.

Для байта с индексом `i`:

```text
output[i] = input[i] XOR key[i mod key_length]
```

Позиция ключа начинается с нуля для каждого файла. Ключ и его длина в архиве
не сохраняются и должны быть переданы извне при распаковке. Пустой ключ запрещён.

## Без FEC

Поток не изменяется, заголовок отсутствует.

## Reed–Solomon

Reed–Solomon не имеет собственного заголовка. Используется систематический
код RS(255,223) над `GF(256)` с порождающим многочленом поля `0x11D`:

```text
[223 байта данных][32 байта чётности]
```

Каждый полный блок исправляет до 16 ошибочных символов. Последний блок
кодируется в укороченной форме: к оставшимся `r` информационным байтам
добавляются те же 32 байта чётности, без нулевого дополнения.

Пусть размер входа FEC равен:

```text
input_size = q × 223 + r, где 0 <= r < 223
```

Тогда размер закодированного потока:

```text
q × 255 + (если r > 0, то r + 32, иначе 0)
```

Декодер выводит размер последнего блока из длины входного `Artifact`.
Остаток длины `1..=32` считается повреждённым форматом. Параметры поля 
и корни генератора являются внутренним форматом rustarch;
размерность RS(255,223), а не полная бинарная совместимость с CCSDS.

## Сводные ограничения

| Параметр                        |                 Ограничение формата |
|---------------------------------|------------------------------------:|
| Длина пути                      |              `0..=65535` байт UTF-8 |
| Число файлов                    |                      `0..=u32::MAX` |
| Число пустых директорий         |                      `0..=u32::MAX` |
| Размер исходного файла в записи |                               `u64` |
| Размер payload в записи         |                               `u64` |
| Абсолютное смещение payload     |                               `u64` |
| Число символов Huffman          |                           `1..=256` |
| LZSS offset                     |      `0..=65535`, сейчас окно 32768 |
| LZSS match length               |                           `3..=258` |
| LZSS literal run                | `1..=65535`, кодер использует от 34 |
